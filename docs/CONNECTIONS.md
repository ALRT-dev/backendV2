# External Connections — `backendV2` (hazard_be)

> Audit of every external service, API, SDK and integration this backend actually
> uses in code. Generated by reading `package.json`, `.env.default`, all config,
> Docker/compose files, and client-initialisation code under `src/`.
>
> **No secret values are printed anywhere in this document.** Only the *names* of
> environment variables and where they are read are listed.

## How configuration is loaded

- Env vars are loaded from `.env.${NODE_ENV}` (defaults to `.env.dev`) — `src/utils/config.ts:6-7`.
- In deployed AWS environments, secrets are pulled at startup from the **AWS Secrets
  Manager Agent** sidecar (`http://localhost:2773`) and merged into `process.env`
  *without* overwriting existing vars — `src/utils/secrets.ts` (called from `config.ts:11`).
  Locally this is a no-op and the `.env` file is used.
- All required/optional env vars are centralised in the exported `config` object —
  `src/utils/config.ts:27-182`.
- `NODE_ENV` values seen in code/scripts: `dev` (default) and `prod`.
  Docker: `docker-compose.dev.yml` uses `.env.dev`; `docker-compose.yml` (blue/green
  prod) uses `.env.prod`.

## 4. Notes on secret handling observed

- Secrets are read from env only; deployed secrets come from the AWS Secrets Manager
  Agent (§1.4), never hard-coded.
- Firebase uses a git-ignored `serviceAccountKey.json` file, not an env var.
- CLI scripts can write one-time secrets to files instead of stdout
  (`WEBHOOK_KEY_OUTPUT_FILE`, `ADMIN_PASSWORD_OUTPUT_FILE`) to avoid CI log leakage.
- No CI workflow files exist in this repo (`.github/` contains only `copilot-instructions.md`).
